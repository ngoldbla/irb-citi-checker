### 1.2 Data Derived (Computed by Extension)

| Data Element | Derivation | Classification |
|---|---|---|
| `isKsuPersonnel` | Institution contains "kennesaw" OR email domain is `kennesaw.edu` / `students.kennesaw.edu` | Non-sensitive |
| Compliance status | 6-rule evaluation engine in `citi-evaluator.ts` | Non-sensitive |
| Deficiency descriptions | Generated text from rule evaluation; includes person's name | Contains **PII** |
| Deficiency recommendations | Generated text from rule evaluation; includes person's name | Contains **PII** |

### 1.3 Data NOT Collected

- Passwords, session tokens, or authentication credentials for Cayuse
- Browser history or activity outside the three KSU Cayuse domains
- Keystroke data, mouse movements, or interaction patterns
- Contents of other browser tabs
- Student academic records (the extension operates on researcher/personnel data)
- IRB submission content beyond personnel and training sections

## 2. Data Storage

### 2.1 Storage Location

All data is stored in `chrome.storage.local`, which is:
- Browser-local (not synced across devices via Chrome Sync)
- Sandboxed per-extension (only this extension can access its storage)
- Backed by the browser's LevelDB/IndexedDB storage on disk

### 2.2 Storage Keys

| Key | Type | Contents | Contains PII? |
|-----|------|----------|---------------|
| `currentSubmission` | `Submission` | Most recent scan result: submission metadata + full personnel array with compliance statuses and training records | **Yes** |
| `submissionHistory` | `Record<string, SubmissionScan[]>` | Map of submission ID to array of historical scan results, each containing full personnel array | **Yes** |
| `settings` | `ExtensionSettings` | `{ portkeyApiKey, portkeyBaseUrl, llmModel }` | **Yes** (API credential) |

### 2.3 Storage Characteristics

| Property | Value |
|----------|-------|
| Encryption at rest | **None.** `chrome.storage.local` stores data unencrypted in the browser's backing store. |
| Access control | Chrome extension sandbox: only this extension ID can read/write. No other extensions, web pages, or content scripts from other extensions can access. |
| Capacity | 10 MB default limit for `chrome.storage.local` (can request `unlimitedStorage` permission, but this extension does not). |
| Persistence | Survives browser restarts. Cleared only on extension uninstall or manual "Clear storage" via `chrome://extensions`. |
| Backup | Not backed up. Lost if browser profile is deleted. |

### 2.4 Sensitive Data in Storage

| Item | Storage Key | Risk |
|------|-------------|------|
| Portkey API key | `settings.portkeyApiKey` | Stored as **plaintext**. Readable by anyone with physical device access or access to browser's backing store files. See [Risk Register SEC-01](06-risk-register.md#sec-01-plaintext-api-key-storage). |
| Personnel names + emails | `currentSubmission.personnel[].name`, `.email` | PII persists indefinitely with no cleanup mechanism. |
| Training records with emails | `currentSubmission.personnel[].citiStatus.trainings[].registeredEmail` | May contain personal (non-institutional) email addresses. |
| Submission history | `submissionHistory` | Grows unbounded. Each scan appends full personnel array. See [Risk Register OPS-02](06-risk-register.md#ops-02-unbounded-submission-history-growth). |

## 3. Data Transmission

### 3.1 Internal Message Passing

All inter-component communication uses Chrome's extension message passing APIs:
- `chrome.runtime.sendMessage()` (side panel <-> service worker)
- `chrome.tabs.sendMessage()` (service worker <-> content script)

This communication is internal to the browser process and never leaves the machine. Data types transmitted include `ScrapedSubmissionData`, `Submission`, and `ExtensionSettings`.

### 3.2 External Transmission

| Field | Detail |
|---|---|
| **Destination** | Portkey API (user-configured base URL + `/chat/completions`) |
| **Protocol** | HTTPS |
| **Authentication** | `Authorization: Bearer <portkeyApiKey>` header |
| **Trigger** | User clicks "Generate Notification" button in side panel |
| **Frequency** | On-demand only; never automatic |
| **Request body** | JSON containing `model`, `temperature` (0.3), `max_completion_tokens` (2000), and `messages` array |

**Data included in LLM prompt** (from `notification-templates.ts`):

| Data Element | Included? | Can Be Minimized? |
|---|---|---|
| Personnel names | Yes | No (needed for email addressing) |
| Personnel roles | Yes | Marginally |
| KSU/External status | Yes | No (context for recommendations) |
| Personnel emails | Yes (in training records) | **Yes** - only needed for `email_mismatch` cases |
| Training course names | Yes | **Yes** - marginally useful context |
| Training completion dates | Yes | No (needed for expiration context) |
| Training expiration dates | Yes | No (needed for expiration context) |
| Training registered email | Yes | **Yes** - only needed for `email_mismatch` cases |
| Protocol number | Yes | No (needed for email reference) |
| Submission title | Yes | No (needed for email reference) |
| Deficiency descriptions | Yes | No (core content) |
| Deficiency recommendations | Yes | No (core content) |

**Data NOT transmitted externally:**
- Portkey API key is sent as a header, not in the prompt body
- Submission history is never sent
- Page URLs are never sent to Portkey
- Settings (beyond what's in the API request) are never sent

## 4. Data Retention

### 4.1 Current State

| Data | Retention | Cleanup Mechanism |
|------|-----------|-------------------|
| `currentSubmission` | Overwritten on each new scan | Implicit (last-write-wins) |
| `submissionHistory` | **Indefinite.** Each scan appends; no TTL, no max entries, no cleanup. | **None** |
| `settings` | Persists until manually changed | User action only |
| LLM notification drafts | Not persisted (rendered in DOM only) | Lost on panel close |

### 4.2 Recommended Retention Policy

- Maximum 10 history entries per submission ID (FIFO eviction)
- Global age-based cleanup: delete history entries older than 90 days
- Add a "Clear All Data" button in the settings modal
- Add a "Clear History" option per submission
- Document that clearing extension data via `chrome://extensions` removes all stored data including API key

## 5. Data Classification Summary

| Level | Elements | Handling Requirements |
|---|---|---|
| **PII** | Personnel names, emails (Cayuse + CITI registered), training records with email | Minimize retention, encrypt at rest (currently a gap), obtain consent before external transmission (currently a gap) |
| **Sensitive Credential** | Portkey API key | Must be encrypted at rest (currently a gap), never logged, transmitted only over HTTPS |
| **Institutional** | Protocol numbers, submission titles, page URLs | Internal use only; do not share outside IRB office |
| **Non-sensitive** | Roles, institutions, compliance statuses, course names, dates, PDF attachment booleans | Standard handling |
